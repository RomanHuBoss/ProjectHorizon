# Project Horizon

**Project Horizon** — процедурный космический симулятор на Godot Engine с исследованием планет, космическими полётами, добычей ресурсов, крафтом, торговлей, заданиями и строительством баз.

Проект разрабатывается как одиночная игра с возможностью последующего расширения архитектуры для серверных функций и кооперативного режима.

## Технологический стек

- **Godot Engine 4.7.1 .NET**
- **C#**
- **.NET SDK**
- **JetBrains Rider**
- **Git**
- **Git LFS**
- **SQLite** через `Microsoft.Data.Sqlite` — для локальных сохранений
- **JSON** — для статических игровых данных
- **Godot Shader Language** — для шейдеров
- **ASP.NET Core** — для будущей серверной платформы

## Целевые платформы

- Windows 10 x64
- Windows 11 x64
- Linux x86_64

Основной рендерер — **Godot Mobile Renderer на Vulkan**.  
Резервный профиль — **Compatibility Renderer на OpenGL 3.3**.

## Текущее состояние

Текущий этап — **Этап 0: независимые технические прототипы**.

### Прототип A. Персонаж — `IN_PROGRESS`

Реализованы плоская тестовая сцена, `CharacterBody3D`, камера от первого лица, WASD, гравитация, прыжок, столкновения, взаимодействие по `E` и простая hitscan-стрельба по ЛКМ. Сцена сохранена в:

```text
src/Game.Client/Scenes/DebugWorld.tscn
```

До приёмки остаются свежая локальная сборка, runtime-проверка стрельбы, полный регрессионный прогон и фиксация Git SHA.

### Прототип B. Чанк рельефа — `IN_PROGRESS`

Реализована тестовая система чанков рельефа:

- отдельная сцена `TerrainChunkPrototype`;
- детерминированный `FastNoiseLite` с OpenSimplex2 и FBM;
- активная сетка `3 × 3` чанка вокруг игрока;
- LOD0 `33 × 33` для чанка под игроком и LOD1 `17 × 17` для внешнего кольца;
- высоты рассчитываются в единых мировых координатах;
- кромки LOD0 геометрически согласуются с соседним LOD1: промежуточные вершины привязываются к линейным сегментам низкого LOD;
- нормали вычисляются по общей глобальной функции высот, поэтому освещение не разрывается на границах чанков;
- skirts создаются только на внешнем периметре активной сетки и не перекрываются на внутренних стыках;
- коллизия создаётся отдельно и сохраняет разрешение `33 × 33` в активной физической зоне;
- смена центрального чанка использует гистерезис, исключающий дребезг возле границы;
- входящие чанки и LOD-обновления рассчитываются в фоне, а исходящие чанки удаляются только после применения готовых результатов;
- смена визуального LOD и масок стыковки не пересоздаёт неизменившуюся collision-сетку;
- поверхность по умолчанию использует матовый vertex-color материал с окраской по высоте и уклону, поэтому форма рельефа и направление нормалей читаются без текстур;
- LOD0 и LOD1 получают различимые диагностические оттенки;
- поверх mesh выводятся непрерывная мировая сетка, реальные рёбра треугольников и цветные границы чанков;
- клавиша `F1` циклически переключает режимы `высота/уклон → LOD → нормали`;
- `F2` включает и выключает мировую сетку, `F3` — wireframe, `F4` — границы чанков;
- диагностические переключатели используют кэш верхней поверхности, перестраивают только visual mesh и overlay, не запускают noise повторно и не затрагивают collision;
- `TerrainChunkDataBuilder` вычисляет noise-высоты, глобальные нормали, UV и индексы в `Task.Run`;
- число параллельных worker-задач ограничено формулой `max(1, min(4, logical_processor_count - 2))`;
- каждый план стриминга имеет `CancellationTokenSource`, каждый job — `jobId` и revision;
- тип узла планировщика явно задан как `Godot.Timer`, а threading-типы подключены точечными alias без конфликта с Godot API;
- при смене плана устаревшие задачи отменяются, а stale-результаты отбрасываются до применения;
- worker возвращает только контейнеры данных, а `Node`, `ArrayMesh`, material и collision создаются в main thread;
- `ConcurrentQueue` передаёт результаты worker в дозированный main-thread apply;
- результаты могут рассчитываться параллельно, но применяются в исходном порядке `create → demotion → promotion → neutral update`, чтобы не создавать временно несовместимую LOD-кромку;
- HUD показывает координату игрока, очередь, активные workers, ошибки, stale-результаты, число чанков, LOD и диагностический режим;
- Output сообщает планирование, запуск/apply job, revision, worker-время, main-thread-время и отмену устаревших результатов.

Активная стартовая сцена:

```text
src/Game.Client/Scenes/Terrain/TerrainChunkPrototype.tscn
```

Пользователь подтвердил предыдущие исправления геометрии и диагностических режимов. После внедрения фоновой генерации локальная сборка выявила конфликт `Timer`; он устранён явным использованием `Godot.Timer` и точечными alias для threading-типов. Перед следующим функциональным шагом требуется повторить сборку, затем проверить возврат HUD к `9/9`, отсутствие применения stale-revision, стабильность collision и значения `worker/main` в Output.

## Архитектурные принципы

Проект использует многослойную архитектуру:

1. **Presentation Layer** — сцены, камеры, UI и визуальные эффекты.
2. **Application Layer** — игровые сценарии и координация систем.
3. **Domain Layer** — правила мира и чистая игровая логика.
4. **Infrastructure Layer** — базы данных, файлы, сеть и логирование.
5. **Tools Layer** — внутренние редакторы, генераторы и диагностика.

Процедурная генерация, экономика, предметы, задания и состояние мира не должны напрямую зависеть от `Godot.Node`.

`Game.Domain` не должен содержать ссылок на Godot.

## Запуск проекта

### Требования

Перед запуском должны быть установлены:

- Godot Engine 4.7.1 .NET;
- .NET SDK x64;
- JetBrains Rider или другая IDE с поддержкой C#;
- Git;
- Git LFS.

Проверка .NET SDK:

```powershell
dotnet --info
```

### Запуск через Godot

1. Открыть Godot Project Manager.
2. Импортировать проект:

```text
src/Game.Client/project.godot
```

3. Дождаться завершения импорта ресурсов.
4. Выполнить сборку C#.
5. Нажать `F5` для запуска активной сцены Прототипа B.
6. Проверить диагностические режимы: `F1` — цвет, `F2` — мировая сетка, `F3` — wireframe, `F4` — границы чанков.
7. Для повторной проверки Прототипа A открыть `Scenes/DebugWorld.tscn` и нажать `F6`.

### Сборка через командную строку

Из корня репозитория:

```powershell
dotnet build .\src\Game.Client\Game.Client.csproj -c Debug
```

## Правила разработки

- основной язык производственного кода — C#;
- `Nullable` должен быть включён;
- предупреждения компилятора должны устраняться;
- зависимости передаются явно;
- асинхронные операции принимают `CancellationToken`;
- SQL-запросы должны быть параметризованы;
- исключения не подавляются;
- запрещены циклические зависимости проектов;
- Godot Node не используется как доменная модель;
- игровая логика не размещается непосредственно в UI;
- SQL не размещается внутри сцен;
- генерация мира не выполняется непосредственно в `_Process`;
- Godot Signals используются для локального взаимодействия сцены;
- доменные события используются для бизнес-логики.

## Ветки Git

Используемая модель ветвления:

```text
main
develop
feature/*
fix/*
release/*
```

- `main` — стабильное собираемое состояние;
- `develop` — интеграционная ветка разработки;
- `feature/*` — разработка отдельных функций;
- `fix/*` — исправления;
- `release/*` — подготовка выпусков.

Пример создания рабочей ветки:

```powershell
git switch develop
git switch -c feature/player-prototype
```

## Git LFS

Git LFS применяется для крупных бинарных файлов, включая:

- исходные 3D-модели;
- крупные текстуры;
- звуковые файлы;
- видео;
- другие тяжёлые бинарные ресурсы.

Правила LFS хранятся в `.gitattributes`.

## Файлы, не включаемые в Git

В репозиторий не должны попадать:

- `.godot/`;
- `bin/`;
- `obj/`;
- `.idea/`;
- локальные настройки IDE;
- временные сборки;
- локальные базы данных;
- журналы;
- секреты и экспортные учётные данные.
