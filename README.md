# Project Horizon

**Project Horizon** — процедурный космический симулятор на Godot Engine с исследованием планет, космическими полётами, добычей ресурсов, крафтом, торговлей, заданиями и строительством баз.

Проект разрабатывается как одиночная игра с возможностью последующего расширения архитектуры для серверных функций и кооперативного режима.

## Технологический стек

- **Godot Engine 4.7.1 .NET**
- **C#**
- **.NET SDK**
- **JetBrains Rider**
- **Git**
- **Git LFS**
- **SQLite** через `Microsoft.Data.Sqlite` — для локальных сохранений
- **JSON** — для статических игровых данных
- **Godot Shader Language** — для шейдеров
- **ASP.NET Core** — для будущей серверной платформы

## Целевые платформы

- Windows 10 x64
- Windows 11 x64
- Linux x86_64

Основной рендерер — **Godot Mobile Renderer на Vulkan**.
Резервный профиль — **Compatibility Renderer на OpenGL 3.3**.

### Прототип C. Сферическая планета — `IN_PROGRESS`

> Build hotfix от 2026-08-01: исправлен некорректный физический перевод строки в HUD floating origin, вызывавший `CS1039/CS1010` при компиляции `CubeSpherePrototype.cs`.

Основа cube sphere, радиальная система игрока и устойчивое прохождение collision-швов приняты по локальным runtime-проверкам. Текущая итерация реализует иерархические локальные координаты и floating origin из раздела 6 PDF-ТЗ:

- локальная ячейка имеет размер `4096 м`;
- перенос выполняется при выходе любой координаты игрока за диапазон `[-2048; 2048] м`;
- координата хранится как `CellX/CellY/CellZ: long` плюс локальный `Vector3`;
- планета, игрок и обзорная камера переносятся одним и тем же вектором без изменения взаимных расстояний;
- логическая позиция вычисляется в `double` как `cell × 4096 + local`;
- сохранённые точки reset и тестовые трансформы корректируются при каждом переносе мира;
- HUD показывает текущую ячейку, локальную позицию и число переносов;
- `Y` запускает автоматическую проверку четырёх переносов по положительным и отрицательным осям;
- acceptance test контролирует шесть переходов ячеек, непрерывность логической позиции, относительные трансформы планеты/игрока/камеры, контакт с поверхностью и восстановление исходного состояния;
- ранее принятый `T`-тест межгранных швов сохранён без изменений;
- `F2` переключает камеру игрока и орбитальный обзор, `F1` — цвета граней и радиальные нормали.

Активная стартовая сцена:

```text
src/Game.Client/Scenes/Planet/CubeSpherePrototype.tscn
```

Ожидаемый результат текущей приёмки:

```text
TASK-032 origin (Y): PASS shifts=4, cells=6, localMax<=2048 m,
logicalErr<=0.01 m, relativeErr<=0.001 m, gap<=0.12 s
```

После подтверждения floating origin следующим кодовым шагом будет quadtree LOD граней и согласование LOD-швов.

## Архитектурные принципы

Проект использует многослойную архитектуру:

1. **Presentation Layer** — сцены, камеры, UI и визуальные эффекты.
2. **Application Layer** — игровые сценарии и координация систем.
3. **Domain Layer** — правила мира и чистая игровая логика.
4. **Infrastructure Layer** — базы данных, файлы, сеть и логирование.
5. **Tools Layer** — внутренние редакторы, генераторы и диагностика.

Процедурная генерация, экономика, предметы, задания и состояние мира не должны напрямую зависеть от `Godot.Node`.

`Game.Domain` не должен содержать ссылок на Godot.

## Запуск проекта

### Требования

Перед запуском должны быть установлены:

- Godot Engine 4.7.1 .NET;
- .NET SDK x64;
- JetBrains Rider или другая IDE с поддержкой C#;
- Git;
- Git LFS.

Проверка .NET SDK:

```powershell
dotnet --info
```

### Запуск через Godot

1. Открыть Godot Project Manager.
2. Импортировать проект:

```text
src/Game.Client/project.godot
```

3. Дождаться завершения импорта ресурсов и выполнить сборку C#.
4. Нажать `F5`; HUD должен показать `Грани: 6/6`, `collision: 6/6`, `швы: PASS` и после стабилизации `Радиальная система: PASS`.
5. Убедиться, что `TASK-030 seam (T): PASS` сохранён как результат принятой предыдущей итерации либо повторно запустить `T` для регрессии.
6. Дождаться `ground=да` и `probe=да`, затем нажать `Y`. Во время автоматической проверки не нажимать WASD, мышь, `Space`, `F2`, `R` или `T`.
7. Дождаться строки `TASK-032 origin (Y): PASS`. Нормальный результат: `shifts=4`, `cells=6`, `localMax <= 2048 м`, `logicalErr <= 0,01 м`, `relativeErr <= 0,001 м`, `gap <= 0,12 с`.
8. Проверить Output: должны присутствовать четыре строки `Floating origin shift` с переходами положительных и отрицательных ячеек и итоговая строка `TASK-032 floating-origin acceptance PASS`.
9. После теста HUD должен снова показывать исходную ячейку и локальную позицию; персонаж, планета и камера не должны визуально дёрнуться относительно друг друга.
10. Проверить `R`, WASD, `Space`, `F1`, `F2` и повторный `T`: предыдущая функциональность должна сохраниться.
11. Повторное `Y` во время теста, а также `F2`, `R` или `T`, должно безопасно остановить проверку и восстановить исходное состояние.
12. Для регрессии Прототипа B открыть `Scenes/Terrain/TerrainChunkPrototype.tscn` и нажать `F6`; `F10` запускает stress-test, `P` — soak-test.
13. Для повторной проверки Прототипа A открыть `Scenes/DebugWorld.tscn` и нажать `F6`.

### Сборка через командную строку

Из корня репозитория:

```powershell
dotnet build .\src\Game.Client\Game.Client.csproj -c Debug
```

## Правила разработки

- основной язык производственного кода — C#;
- `Nullable` должен быть включён;
- предупреждения компилятора должны устраняться;
- зависимости передаются явно;
- асинхронные операции принимают `CancellationToken`;
- SQL-запросы должны быть параметризованы;
- исключения не подавляются;
- запрещены циклические зависимости проектов;
- Godot Node не используется как доменная модель;
- игровая логика не размещается непосредственно в UI;
- SQL не размещается внутри сцен;
- генерация мира не выполняется непосредственно в `_Process`;
- Godot Signals используются для локального взаимодействия сцены;
- доменные события используются для бизнес-логики.

## Ветки Git

Используемая модель ветвления:

```text
main
develop
feature/*
fix/*
release/*
```

- `main` — стабильное собираемое состояние;
- `develop` — интеграционная ветка разработки;
- `feature/*` — разработка отдельных функций;
- `fix/*` — исправления;
- `release/*` — подготовка выпусков.

Пример создания рабочей ветки:

```powershell
git switch develop
git switch -c feature/player-prototype
```

## Git LFS

Git LFS применяется для крупных бинарных файлов, включая:

- исходные 3D-модели;
- крупные текстуры;
- звуковые файлы;
- видео;
- другие тяжёлые бинарные ресурсы.

Правила LFS хранятся в `.gitattributes`.

## Файлы, не включаемые в Git

В репозиторий не должны попадать:

- `.godot/`;
- `bin/`;
- `obj/`;
- `.idea/`;
- локальные настройки IDE;
- временные сборки;
- локальные базы данных;
- журналы;
- секреты и экспортные учётные данные.
