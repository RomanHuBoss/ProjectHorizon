> **Назначение:** единая точка контроля соответствия проекта техническому заданию.  
> **Актуальная ветка на момент создания:** `feature/player-prototype`  
> **Исходный снимок для первичного аудита:** `ProjectHorizon-feature-player-prototype.zip`  
> **Дата первичного аудита:** 2026-07-31  
> **Ответственный за актуализацию:** разработчик, выполняющий коммит  
> **Правило:** изменение кода или сцен без обновления этого журнала считается незавершённой задачей.

## 1. Как пользоваться журналом

Каждое требование получает внутренний стабильный идентификатор. Идентификатор не заменяет номер раздела ТЗ, а связывает требование с кодом, сценами, тестами и коммитами.

### Статусы

| Статус | Значение |
|---|---|
| `NOT_STARTED` | Реализация не начиналась |
| `IN_PROGRESS` | Работа начата, но требование ещё не выполнено полностью |
| `IMPLEMENTED` | Реализация существует, но ещё не прошла полный набор проверок |
| `VERIFIED` | Требование реализовано и подтверждено доказательствами |
| `BLOCKED` | Работа невозможна до устранения явно указанной блокировки |
| `DEFERRED` | Требование осознанно перенесено на более поздний этап ТЗ |
| `N/A` | Требование неприменимо к текущей конфигурации; требуется обоснование |

### Что необходимо для статуса `VERIFIED`

Статус `VERIFIED` разрешён только при наличии всех применимых подтверждений:

1. **Реализация** — файл, сцена, ресурс, конфигурация или код существуют.
2. **Сборка** — соответствующий проект собирается без ошибок.
3. **Автоматическая проверка** — unit/integration/smoke test, если требование тестируемо автоматически.
4. **Ручная проверка** — конкретный воспроизводимый сценарий, если это игровое поведение.
5. **Git-доказательство** — ветка и хеш коммита, содержащего проверенную реализацию.
6. **Отсутствие открытых дефектов**, нарушающих требование.

Наличие файла само по себе означает максимум `IMPLEMENTED`, но не `VERIFIED`.

## 2. Обязательный формат записи доказательств

Для каждого завершённого требования указываются:

```text
Файлы:
Сцены/узлы:
Автотесты:
Ручная проверка:
Команда сборки:
Результат:
Ветка:
Коммит:
Проверил:
Дата:
Открытые ограничения:
```

Пример:

```text
Файлы: src/Game.Client/Scripts/Player/PlayerController.cs
Сцены/узлы: Scenes/Player/Player.tscn → Player
Автотесты: отсутствуют, поведение проверяется smoke test
Ручная проверка: WASD, обзор мышью, прыжок, повторный прыжок после приземления
Команда сборки: dotnet build .\src\Game.Client\Game.Client.csproj -c Debug
Результат: 0 ошибок, 0 предупреждений
Ветка: feature/player-prototype
Коммит: <полный или сокращённый SHA>
Проверил: <имя>
Дата: YYYY-MM-DD
Открытые ограничения: отсутствуют
```

### Следующее обязательное действие

До программирования WASD и прыжка необходимо привести базовую сцену и конфигурацию проекта в согласованное состояние:

1. удалить отдельную `DebugWorld/Camera3D`;
2. оставить единственную камеру `Player/Head/Camera3D`;
3. добавить `DirectionalLight3D`;
4. изменить Windows rendering driver с `d3d12` на `vulkan`;
5. включить `<Nullable>enable</Nullable>`;
6. собрать проект без ошибок;
7. вручную запустить `DebugWorld`;
8. зафиксировать результат отдельным коммитом;
9. обновить доказательства в этом журнале.

Рекомендуемый коммит:

```text
fix: align debug scene and project settings with technical specification
```

**Основание:** архив `ProjectHorizon-feature-player-prototype.zip`.

## 14. Правила обновления при каждом коммите

Перед коммитом:

1. определить связанные ID требований;
2. обновить статус только фактически изменившихся требований;
3. записать доказательства;
4. обновить раздел «Очередь ближайших задач»;
5. выполнить сборку и применимые тесты;
6. сделать коммит;
7. после коммита вписать его SHA дополнительным коммитом журнала либо включить SHA предыдущего коммита в следующую запись.

Рекомендуемый формат сообщения коммита:

```text
<type>: <краткое действие>

Requirements: PA-020, PA-021, PA-022
Verification: dotnet build; manual movement smoke test
```

Допустимые типы:

```text
feat
fix
test
docs
refactor
chore
build
ci
perf
```

## 15. Определение следующего шага

Следующий шаг выбирается по следующему правилу:

1. найти первый `BLOCKED` или `IN_PROGRESS` пункт текущего этапа;
2. проверить, блокирует ли он другие требования;
3. выбрать минимальную задачу, после которой можно получить проверяемый результат;
4. не переходить к следующему этапу, пока критерии приёмки текущего этапа не имеют статус `VERIFIED`.

На момент первичного аудита:

```text
Следующий шаг = TASK-001:
удалить отдельную DebugWorld/Camera3D
```
