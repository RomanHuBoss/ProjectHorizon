# Регламент выполнения итераций разработки Project Horizon

## 1. Назначение

Настоящий документ определяет обязательный порядок выполнения каждой следующей
итерации разработки Project Horizon.

Регламент применяется совместно с:

- актуальной PDF-версией технического задания;
- `REQUIREMENTS_STATUS.md`;
- последней редакцией проекта, полученной из GitHub и приложенной к запросу;
- ранее подтверждёнными пользователем результатами runtime-проверок.

Последняя приложенная редакция проекта является исходной кодовой базой текущей
итерации. Если в диалоге уже подтверждена приёмка реализованной функции, журнал
сначала синхронизируется с этим доказательством, а затем выбирается новый шаг.

---

## 2. Определение следующей итерации

Перед внесением изменений необходимо:

1. Распаковать последнюю приложенную редакцию проекта.
2. Найти актуальную PDF-версию технического задания.
3. Изучить `REQUIREMENTS_STATUS.md`.
4. Учесть результаты сборок, скриншоты, строки Godot Output и ручные подтверждения
   пользователя из текущего диалога.
5. Определить ближайшую незавершённую задачу с учётом:
   - порядка задач;
   - зависимостей;
   - приоритетов технического задания;
   - ранее выявленных дефектов;
   - необходимости сначала завершить приёмку уже реализованной функции.

Если пользователь предоставил достаточное доказательство работоспособности
задачи со статусом `IMPLEMENTED`, соответствующая задача и её приёмочная задача
переводятся в `VERIFIED` до выбора следующего функционального шага.

Нельзя повторно реализовывать уже подтверждённую функцию без отдельной причины.

---

## 3. Статусы задач

В журнале используются следующие статусы:

- `NOT_STARTED` — реализация не начиналась;
- `PLANNED` — задача сформулирована и поставлена в очередь;
- `IN_PROGRESS` — работа начата либо выполняется приёмка;
- `IMPLEMENTED` — код реализован, но runtime-приёмка ещё не подтверждена;
- `VERIFIED` — реализация подтверждена сборкой и необходимой runtime-проверкой;
- `BLOCKED` — выполнение невозможно до устранения указанной зависимости;
- `DEFERRED` — требование осознанно перенесено;
- `SUPERSEDED` — задача заменена другой реализацией;
- `N/A` — требование неприменимо с указанным обоснованием.

Статус `VERIFIED` нельзя назначать только по результатам статического анализа,
если задача требует запуска в Godot.

---

## 4. Требования к реализации

В рамках одной итерации необходимо:

1. Реализовать один логически завершённый функциональный шаг.
2. Не вносить несвязанные изменения без необходимости.
3. Не удалять существующую функциональность, если это прямо не предусмотрено ТЗ.
4. Сохранять совместимость с текущей структурой проекта.
5. Учитывать ранее исправленные дефекты и не допускать их возврата.
6. Соблюдать архитектурные ограничения PDF-ТЗ.
7. Не обращаться к Godot API, `SceneTree`, узлам, mesh или collision API из
   фоновых потоков, если это запрещено принятой архитектурой.
8. Не добавлять build-артефакты, кэш IDE и временные файлы в итоговый архив.
9. Использовать корректные пути `res://` для новых ресурсов и сцен.
10. Отражать новые пользовательские горячие клавиши в HUD и README.
11. Не скрывать известные ограничения, предупреждения компилятора и непроверенные
    предположения.

---

## 5. Сборка и проверки

После реализации выполняется максимально доступный набор проверок:

- статическая проверка изменённых C#-файлов;
- проверка незавершённых строковых констант;
- проверка сбалансированности скобок и комментариев;
- проверка nullable-предупреждений в изменённом коде;
- проверка ссылок `res://`;
- проверка структуры сцен и NodePath;
- проверка отсутствия конфликтующих горячих клавиш;
- проверка содержимого и целостности ZIP;
- сборка .NET-проекта, если среда содержит необходимый SDK;
- запуск Godot и runtime-тест, если среда это позволяет.

Если сборку или runtime-проверку выполнить невозможно, это прямо указывается.
Нельзя заявлять об успешной сборке или работе функции без фактического запуска.
Предупреждения компилятора фиксируются как технический долг, даже если сборка
завершилась успешно.

---

## 6. Обновление журнала реализации

В каждой итерации обновляется `REQUIREMENTS_STATUS.md`.

Журнал должен содержать:

- дату итерации;
- номер и название задачи;
- исходный и подготовленный снимки;
- изменённые файлы;
- краткое описание реализации;
- затронутые требования PDF-ТЗ;
- проведённые проверки;
- фактические показатели runtime-приёмки;
- известные ограничения и технический долг;
- изменения статусов;
- следующий рекомендуемый шаг;
- критерии пользовательской приёмки новой функции.

Если пользователь предоставил скриншот или текст результата проверки, в журнал
вносятся конкретные показатели, например:

```text
PASS
crossings=4
gap=0,00 с
deltaUp=0,59°
errors=0
```

Недостаточно записать только формулировку «пользователь подтвердил работу».

---

## 7. Доказательство работоспособности

Для каждой новой функции заранее определяется воспроизводимый способ runtime-
проверки.

Проверка по возможности должна включать:

- отдельную горячую клавишу запуска;
- состояние `RUNNING`;
- финальный результат `PASS` или `FAIL`;
- измеримые показатели и допустимые пределы;
- вывод результата в HUD;
- дублирование итоговой строки в Godot Output;
- безопасную остановку;
- восстановление исходного состояния после теста.

В итоговом ответе пользователю необходимо точно указать:

1. Как запустить тест.
2. Сколько времени он занимает.
3. Какой результат считается успешным.
4. Какие показатели должны присутствовать в HUD.
5. Какой скриншот необходимо прислать.
6. Какую строку необходимо скопировать из Godot Output.
7. Какие действия необходимо проверить вручную.
8. Какие данные прислать при `FAIL`.

Нельзя требовать неопределённое подтверждение вида «проверьте, что всё работает».

---

## 8. Итоговый архив

По завершении итерации необходимо:

1. Обновить исходный код.
2. Обновить `REQUIREMENTS_STATUS.md`.
3. Обновить README, если изменились запуск, управление, горячие клавиши,
   архитектура, диагностика или порядок проверки.
4. Исключить из архива:
   - `.godot`;
   - `bin`;
   - `obj`;
   - `.vs` и кэш IDE;
   - временные файлы;
   - локальные логи и базы данных, не являющиеся частью документации;
   - `.git`.
5. Проверить ZIP на целостность.
6. Вычислить SHA-256.
7. Передать пользователю ссылку на итоговый архив.

Рекомендуемый формат имени:

```text
ProjectHorizon-main-<краткое-название-итерации>.zip
```

---

## 9. Обязательное содержание итогового ответа

Итоговый ответ должен содержать следующие разделы.

### Выполненная итерация

- номер задачи;
- краткое название;
- статус;
- основные изменения.

### Проверки

- что было проверено фактически;
- была ли выполнена сборка;
- был ли выполнен runtime-тест;
- какие ограничения среды или предупреждения остались.

### Архив

- ссылка на ZIP;
- SHA-256.

### Доказательство работоспособности

- пошаговая инструкция;
- ожидаемый `PASS`;
- допустимые показатели;
- требуемый скриншот;
- требуемая строка Godot Output;
- пункты ручной проверки;
- сведения, необходимые при `FAIL`.

### Текст коммита

Предоставляется готовый commit message в формате Conventional Commits:

```text
<type>(<scope>): <краткое описание>

- изменение 1
- изменение 2
- изменение 3
- обновить README и журнал реализации требований
```

Допустимые типы: `feat`, `fix`, `test`, `refactor`, `perf`, `docs`, `chore`.

---

## 10. Критерий завершения итерации

Итерация считается переданной пользователю только при наличии:

- обновлённого кода или явно заявленной документационной итерации;
- обновлённого журнала;
- целостного ZIP-архива;
- описания изменений;
- инструкции по приёмке новой функции;
- измеримых критериев `PASS/FAIL`;
- готового текста коммита.

Функциональная итерация окончательно завершается и переводится в `VERIFIED`
после получения достаточного доказательства работоспособности от пользователя.

---

## 11. Стандартный запрос на следующую итерацию

После включения настоящего регламента в репозиторий достаточно использовать
следующий запрос:

```text
Выполни следующую итерацию разработки Project Horizon по регламенту
`DEVELOPMENT_ITERATION_PROTOCOL.md`, PDF-ТЗ и `REQUIREMENTS_STATUS.md`.

Последняя редакция проекта, скачанная с GitHub, приложена к сообщению.
```
